## What changed

CLAUDE.md has always said *every change to `skills/`, `agents/`, `hooks/` or
`scripts/` is a release*, and named `test-docs-consistency.sh` as the
enforcement. That gate reads the version out of `plugin.json` and asserts a
matching note exists — the **converse**. It can only see releases that were
declared; nothing ever asked where the bump was. Two misses in one day, both
green at the time:

- **PR #85** changed `scripts/gate.sh` and `scripts/test-gate.sh` with no bump
  and no note. It shipped because a human read the body.
- **The 0.61.0 renumber** left the update workflow's shipped `::error::` telling
  a refused third-party repo to go read the note for the slice's pre-renumber
  number — a file nobody ever wrote, quoted to a reader who cannot see this tree.

Two gates now, each watched red before its green.

### `scripts/check-release-bump.sh` — a release-bearing path implies a release

If the diff against the merge base touches `skills/`, `agents/`, `hooks/` or
`scripts/`, `.claude-plugin/plugin.json`'s version must be **ahead of** the
base's and `upgrades/v<new>.md` must exist. Base resolution is
`check-test-pairing.sh`'s, verbatim, so the two gates cannot disagree about what
"the base" is.

**Ahead of, not merely different from.** Written as "different" the rule passes
PR #85 unchanged: that branch was cut before `main` moved and carries 0.58.0
against a base of 0.61.0, so its version differs and the weaker rule reports OK.
The test watched that happen before the rule tightened, and its last arm replays
PR #85 from real history against its real base.

The escape hatch is `SKIP_RELEASE_BUMP=<reason>`. It takes the **reason**, not a
`1`: a bare truthy value exits 2 asking for one. An exception is a debt, and the
reason is what makes it payable — and what puts it in the diff.

### `scripts/check-version-citations.sh` — a pointer resolves

A citation that **sends a reader to** an upgrade note must name a note that is
there. A pointer is a link whose target is the note, or a
`see`/`read`/`follow`/`consult`/`refer to` immediately before its path.

The design problem is everything this does **not** check. This repo's prose
names old versions constantly and legitimately — upgrade notes reference
predecessors, the backlog says "shipped v0.42.0", learnings carry versions in
`evidence=`. Counted on the tree this shipped with, exactly one cited note is
absent, and **both of its citations sit in the backlog entry describing this
very defect**. A rule keyed on the version appearing reddens on the description
of the bug it exists to catch, and the only way out of that is an exclusion
list. So the rule grades the claim the text makes: naming a version asserts
nothing about the file system, sending someone to a file asserts it is there.
Only the second is checkable, and only the second was ever wrong.

Proven on the real corpus rather than a fixture: green on the tree as it stands
(4 pointers, all resolving, no exclusions), red on that same tree with the
shipped `::error::` put back the way the renumber left it.

Its known ceiling: it catches a **dead** destination, not a *wrong* one. A
pointer naming a note that exists but belongs to another release reads as green.
The renumber produced a dead one; that is the case with evidence behind it.

### `.github/workflows/validate-plugins.yml`

Both gates wired in — the bump check on pull requests, where a merge base
exists; the citation check on every event. The `paths:` filters are **gone**.
They enumerated directories one gate at a time and were already wrong once (they
excluded the workflow `check-supply-chain-pin.sh` guards, so half of PR #81
changed with the gate never running). `check-version-citations.sh` reads every
tracked file, and no enumeration can be right for a whole-tree corpus — `CLAUDE.md`
alone sat outside the old list. A filter and that corpus cannot both be correct.

## Nothing to do

No skill, agent, hook or installed surface changed. The gates run in this repo's
CI on this repo's own diffs; a repo that installs flywheel sees no difference.
