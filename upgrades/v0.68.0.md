## What changed

`.github/workflows/validate-plugins.yml` discovers `scripts/test-*.sh` with a
glob, under a comment explaining exactly why: *"so a new one cannot sit in the
tree never executed (which is what happened to test-run-cost.sh for four
releases)"*. Six lines below that comment, the `check-*.sh` gates are a
hand-written list of steps — and the same failure had already happened to them:

> **`scripts/check-supply-chain-pin.sh` was invoked by no workflow.** Its own
> header calls it *"the only Critical in the pillar-2 threat model"*. It appears
> in `.github/workflows/` exactly twice, and both are **comment lines**. It has a
> test, it passes, it has been green in every local sweep, and it had never once
> run in CI.

Nothing was wrong with the gate. Nothing was ever wired.

**`scripts/check-ci-gate-parity.sh`** now asserts both directions: every
`check-*.sh` in the tree is invoked by some workflow, and every gate a workflow
invokes exists in the tree (so a green parity cannot be bought by renaming a
step). It is the third gate of this shape, after `check-hook-parity.sh` and
`check-agent-parity.sh`.

**Stripping comments is the gate, not a detail of it.** To anything that greps
`.github/workflows/` without stripping comment lines, the tree read as fully
wired — which is precisely how this survived.

**The hand-written list stays.** Replacing it with a glob loop would call
`check-test-pairing.sh` and `check-release-bump.sh` without their merge-base
argument, leaving them green having compared nothing — this ledger's oldest
mistake wearing a different hat. Named steps also carry per-gate annotations in
the CI UI. The list was never the defect; the list being unchecked was.

Both the Critical gate and the new parity gate are wired in the same change, so
the rule polices its own enforcement: unwire it and it fails on itself.

Nothing to do on upgrade. A repo that vendors flywheel gets the gate with the
next install; it only reports on `.github/workflows/` and `scripts/check-*.sh`.
