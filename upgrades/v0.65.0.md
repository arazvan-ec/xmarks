## What changed

Three changes from one measurement. A real debug session was metered end to
end: 2h40m, 21,404,993 cache-read tokens against 120,280 written — **178 read
for every one produced** — and a bill whose largest line, 58%, was not thinking
and not writing but re-reading context. Its output was 10 commits over three
merged PRs: four of instrumentation, three of documentation, three candidate
fixes, **zero verifications**.

Two different defects produced that, and neither is "the session read too much".

### The cost of a session grows with its own length

Every tool call re-sends the whole accumulated context. In that session the
first call re-read ~30K tokens and the last re-read 279,203 — the same work,
nine times the price, for no reason but its position in the transcript. Split
into three chained sessions the identical call sequence costs 9.9M cache-read
tokens instead of 21.3M. Reading less cannot reach that number; only ending the
session can.

`scripts/read-meter.sh` already held the running total, so it now says so. Past
a budget it emits a `PostToolUse` advisory: write the handoff — what is done,
what is next, the first file the next session should read — commit it, and end.

- Fires **once per multiple** of the budget. Once is an advisory; every call is
  noise that costs the very context it is warning about.
- `FLYWHEEL_CONTEXT_BUDGET_BYTES` overrides the 600 KB default; `0` disables it.
  600 KB is where the marginal cost of one more call (context × the cache-read
  rate) passes the fixed cost of writing a handoff and re-priming a fresh
  session — about 150K tokens of context, at the ~4 B/token this floor counts.
- The advisory is a **read** of the total the meter already recorded, never a
  second measurement. Asserted explicitly: a meter that counted its own warnings
  would inflate the `bytes_in` and `tool_calls` it exists to report.

### Evidence you cannot obtain suspends the debug loop

`/flywheel:debug` step 3 said *run it and read the actual evidence*, which
silently assumes the session can run it. When the log lives on a phone, in
production, or behind a person, it cannot — and the skill named no other move,
so the session instrumented, guessed, instrumented again, each round re-reading
the last one's context. That is the whole shape of those three PRs.

Step 3 now names the suspend: commit the instrumentation **as** instrumentation,
say in the PR what it will discriminate and what the suite structurally cannot,
and end the session. Two bans close the exits taken instead of it:

- **A second instrumentation round with no new evidence between them.** Two
  rounds mean the first one's evidence never arrived; a third is guessing with
  extra steps.
- **Raising effort or model tier to compensate for a missing discriminator.**
  With nothing able to kill a hypothesis, more reasoning produces more
  candidates, not fewer. That session spent ~$3 of reasoning at `xhigh` doing
  exactly this.

### The meter was dropping the responses that matter (fix)

Found while building the budget. The hook payload reached python through an
**environment variable**; a single env string is capped at 128 KiB on Linux and
the exec fails *whole*, so every tool response above the cap was never recorded
— the largest reads, which are the ones that fill the context. The `2>/dev/null`
on the block made it invisible. `bytes_in` has described itself as a floor since
P44 while carrying a hole in the middle of what it measures; any run that read a
large file under-reports, and nothing said so.

The payload now reaches python through a file. The assertion feeds 200 KB and
requires the total to say `200000`.

## Nothing to do

The budget is on by default and needs no configuration; set
`FLYWHEEL_CONTEXT_BUDGET_BYTES` only to move or disable it. A vendored install
picks all three up with `/flywheel-update`. Telemetry already written is
unaffected, though `bytes_in` recorded before this release under-reports any
transition that read a file larger than 128 KiB — a known floor, not backfilled.
