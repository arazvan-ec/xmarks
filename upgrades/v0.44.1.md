## What changed

- **`scripts/install-vendored.sh`**: vendors `delegation-guard.sh` and
  `delegation-record.sh` into `.claude/flywheel/bin/`, registers them in the
  target's `.claude/settings.json` (`PreToolUse` and `PostToolUse` on
  `mcp__.*__create_session|Agent|Task`), and removes both again on
  `--uninstall`.

- **`scripts/test-install-vendored.sh`**: asserts both scripts are vendored and
  executable, that each is registered exactly once with its matcher, and — via
  the existing uninstall assertion — that `settings.json` returns to its
  pre-existing content, which now also covers the two new entries.

## Why 0.44.0 was half-installed

There are two delivery paths and they are wired differently. An **installed**
plugin gets its hooks from `hooks/hooks.json`, which 0.44.0 updated. A
**vendored** repo — the documented path for Claude Code on the web, because web
sessions do not install marketplace plugins — is wired by `install-vendored.sh`,
whose list of hook commands is hand-maintained. 0.44.0 updated the first and not
the second.

The failure would have been silent in the worst way: `bin/*` is copied from an
explicit file list, so the scripts would not even have landed, and nothing
checks that a hook a repo expects is actually registered. A guard that is
installed but never fires is indistinguishable from a guard that has nothing to
warn about.

The repo's own conventions caught neither, for the same reason: the
script↔test pairing gate confirms a *changed* script moved with its test, and
`install-vendored.sh` was not changed in 0.44.0. The gap was in what the
installer's test asserted, and that is what this release closes — the test now
fails if either hook is copied but left unregistered.

## Action required

None beyond re-vendoring (`/flywheel:update`), which is what picks the hooks up.
A repo that already refreshed to 0.44.0 should refresh again: 0.44.0 left it
without the guard.
