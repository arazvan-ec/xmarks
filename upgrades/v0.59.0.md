## What changed

P13 slice 1 closes B10, the only **Critical** in the pillar-2 threat model.

`install-vendored.sh --auto-update` writes a caller workflow into your repo. That
caller invoked flywheel's reusable workflow, which ran
`git clone --depth 1 .../xmarks` and `bash`ed the result under `contents: write`
+ `pull-requests: write`, weekly, on a cron nobody watches. Anyone who could push
to flywheel's `main` could run arbitrary code in your repository's CI, unattended
and with write access — and because the installer rewrites your hooks into
`.claude/flywheel/bin/`, the same compromise owned your SessionStart path too.

Pinning the caller's `uses:` would **not** have closed this. A pinned workflow
that still clones a moving branch executes the branch. Both halves changed:

- **The caller pins a full commit SHA** and passes that same commit as a new
  `flywheel_sha` input. One variable in the installer fills both, so they cannot
  disagree.
- **The reusable workflow fetches and checks out that commit**, and refuses —
  before any vendored bash runs — if the input is absent or is not a full 40-hex
  SHA.
- `actions/checkout` and `peter-evans/create-pull-request` are pinned to commit
  SHAs.
- `scripts/check-supply-chain-pin.sh` is a new CI gate asserting **both** halves
  independently, so a later edit cannot quietly reopen either one.

**What this buys, and what it does not.** Pinning converts unattended RCE into a
reviewable diff: a compromised flywheel release can no longer reach your repo by
itself. It does **not** make a compromised release safe once you choose to move
to it — it makes that choice yours, and explicit.

## Strategy

**Every repo installed with `--auto-update` before 0.59.0 is affected, and its
weekly update job will start failing.** Your caller says `@main` and passes no
`flywheel_sha`, and the reusable workflow now refuses that caller rather than
serving it. This is deliberate: an `@main` caller cannot be made safe, so it
fails loudly instead of continuing to run unpinned code in your CI.

Note the awkward part honestly: the mechanism that delivers these upgrade notes
*is* the mechanism that stops. If you are reading this in an automated update PR,
you are already past it. If your flywheel updates simply went quiet, this note is
why, and nothing will bring it to you — someone has to come looking.

To fix, re-vendor from a flywheel checkout at the version you want:

```
git clone https://github.com/arazvan-ec/xmarks
bash xmarks/scripts/install-vendored.sh --auto-update /path/to/your/repo
```

Commit the rewritten `.github/workflows/flywheel-update.yml`. It will now carry a
40-character SHA in two places; they must stay identical.

**Then read the pin as a trust decision, because that is what it now is.** After
this, *the pin is the update lever*: this workflow refreshes your vendored copy
to match whatever commit your caller names, and nothing moves that commit for
you. Automatic **discovery** of new flywheel versions is gone — closing the
supply-chain hole and keeping automatic discovery are not the same task, and
slice 1 only does the first. To take a newer flywheel, bump both occurrences of
the SHA (or re-run the installer from a newer checkout) and let the workflow do
the mechanical refresh.

If you would rather not pin, remove `.github/workflows/flywheel-update.yml` and
re-vendor manually when you want a new version. There is no supported
configuration that keeps the old unattended behaviour, because that behaviour is
the vulnerability.
