## What changed

Three defects of one shape: a rule that is right on its own and inconsistent
with the gate beside it. None of them is a new feature; each is a place where
two gates answered the same question differently.

### An unstarted cycle is not a missing record

v0.70.0 taught `check-task-closure.sh` that a task with no transition line is
**PENDING**, because the loop commits a plan at its approval gate *before* the
work. Its sibling `check-route-honored.sh` still called that task
**UNRECORDED** and failed it, so a plan-only commit stayed red and the fix
bought nothing.

`NOT STARTED` is now a notice there, and a different claim from UNRECORDED. The
discriminator is the one already shipped: **no** line for **any** task means the
cycle has not started; **some** lines with a gap means it ran and the record is
missing, which stays fatal. That second half is what keeps P49 alive, and the
arm proving it — T1 recorded, T2 not, exit 1 — was already in the suite and
stayed green throughout.

The first thing this unblocked was real: `.claude/flywheel/specs/list-intake.plan.md`
had been written and held out of the repo for exactly this reason, and lands
here.

### The pairing gate sees every script language

`check-test-pairing.sh` globbed `scripts/*.sh`. v0.70.0 added `scripts/fw_tasks.py`,
the repo's first `.py` under `scripts/`, and the gate **could not see the file at
all** — the arm written to prove it came back "no script changes". A script can
land with no test while the suite reports everything paired, which this ledger
already records happening once before, on a branch of `install-vendored.sh`.

The pair is keyed on the **stem** now: `scripts/<stem>.<ext>` pairs with
`scripts/test-<stem>.sh`, because a `.py` subject is exercised by a `.sh`
harness like everything else here. Data files (`*.txt`) are deliberately not
listed — they are not scripts. `test-fw-tasks.sh` was renamed `test-fw_tasks.sh`
so it matches its subject.

### The cutoff instant is declared once (P54b)

P54(b) named a date literal duplicated in two gates behind two env vars, "so one
can move without the other". By v0.70.0 there were **three**, and nothing stated
that two of them share a date *on purpose* because one decision (P48) placed
both.

`scripts/cutoffs.txt` declares each cutoff with its reason; `scripts/fw_cutoffs.py`
resolves it, env var first. Two guards, because either failure mode is silent:
an unknown name **raises** and an env var that is set but empty **falls
through**, since returning `""` compares true against every timestamp and would
forgive the entire corpus without saying anything.

Extraction is not a policy change, so `scripts/test-fw_cutoffs.sh` **pins all
three against their pre-extraction literals**. Moving one now has to be argued
in the registry row and in that test together. Verified byte-identical: both
gates still report `2026-09-17T20:00:00Z`.

P54(a) — *what* `check-route-honored.sh` should call fatal rather than a notice —
is untouched. That is a policy question for the owner, not a coherence bug.

Nothing to do on upgrade. A vendored install picks up `fw_cutoffs.py` and
`cutoffs.txt` with the next `install-vendored.sh` run, and the test asserts the
vendored pair actually resolves rather than merely existing.
