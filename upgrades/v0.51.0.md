## What changed

- **`skills/run/SKILL.md` step 2 — two failures, named apart.**
  - **This input cannot satisfy the contract** → the Guardrails' partial-failure
    path, unchanged. Never fabricate a field to make the output look complete.
  - **No input could**, because Rules, Output schema and Persistence contradict
    each other → a **contract defect**, which is *not* a rejection: filing it as
    one mislabels a valid input. Stop as a blocker, **never rewrite the fixed
    rules** to make this input pass, and **escalate**.

- **The escalation is a spec stub**, seeded from the run's own evidence and
  applying nothing — no contract edit, no version bump, no Improvement log
  entry. Its shape is in `skills/run/references/ledger-and-extensions.md`: the
  two conflicting clauses quoted verbatim in **R**, the input that exposed them
  in **Safeguards**, the contract version in **N**, and **A**/**O** left open,
  because the fix is a decision and guessing it is the rewrite this path refuses.

- **`scripts/invocation-budget.txt`** — `run` gains a `worst` exception
  (9,200 → 11,000), the first created since P36.

## Why this existed

Building v0.50.0's eval produced a contract that contradicted itself: its Output
schema capped `digit_sum` at `0–27` while its own Rule 3 computes a sum reaching
36. Two fresh-context executors ran it and did **opposite** things, neither
breaking a stated rule. One proceeded with the true value and matured the
contract to widen the bound. One refused to emit a non-conforming output *and*
refused to mature, holding that a schema change with a version bump is not a
blocked run's call.

The second is right on the skill as written. The skill then offered that run
nothing to do next — so a real defect in a real contract died in a transcript,
and the next run walked into the same wall.

**When two competent runs disagree and neither broke a rule, the skill is
silent.** That is what this release fixes.

## Why the run may not fix the contract, even when the fix is obvious

It *was* obvious — four digits sum to at most 36, so the bound was simply wrong,
and one executor corrected it. The reason to refuse anyway: *obvious* is the
runtime's judgment about the document whose whole purpose is to constrain that
judgment. **A contract a run may edit under pressure is a suggestion.**

Eval 5 was **red before the change**: the run blocked correctly and had nowhere
to put its evidence.

## Why the ceiling moved, and what was tried first

`run` is a five-step contract runtime — three references plus a body of nothing
but rules — and the 9,200 `worst` default was calibrated against skills carrying
none of that. The exception was reached only after the recorded order was
exhausted **twice in this slice**: a first draft of the stub section restated
`/flywheel:spec`'s own REASONS canvas (−559 B), and a reference section
repeating the body's framing moved to the uncited rationale doc (−260 B). What
remained was procedure that exists nowhere else.

## Two things observed, not fixed

- **`run` step 0 prescribes a surface that has never once existed.** Every run
  this session — eight of eight — reported no host task system, so "materialize
  each contract Rule as a visible task" silently became the JSONL ledger. The
  fail-open is working as designed; whether a rule that never fires should stay
  written as the primary path is a question for a later slice.
- **The contract's `metric` covers only the success path**, so a run ending in a
  rejection has nothing declared to verify itself against. Found by eval 3's
  executor, which correctly declined to act on it (the skill caps maturation at
  one refinement per run).
