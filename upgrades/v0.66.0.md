## What changed

`read-meter.sh` has recorded `{ts, tool, bytes}` for every tool call since
v0.56.0, and `--since` collapsed all of it into one total. The measurement
existed; only the aggregate survived. That is why P40b — routing expensive reads
behind an extractor — was **rejected as unjustified rather than disproven**, with
the ledger recording the reason:

> the largest single read in 619 calls is bounded only to [4,898 ; 152,232]
> bytes, straddling P40b's 8 KB threshold by 18x

`--since` now also prints:

- **`max_read=<N>`** — the largest single tool response in the window.
- **`by_tool=<Tool>:<bytes>/<calls>,…`** — the total attributed to the tools that
  caused it, biggest first. A write tool appears with **0 bytes and a real call
  count**, exactly as v0.56.0 defined it: the call happened, the bytes never
  entered context.

Nothing new is measured, and no hook changed — this is a reporting change on data
already being kept, which is why it ships without touching the half of the script
that runs on every tool call.

`run-cost.sh` splits its fields into `SUM_FIELDS` and `MAX_FIELDS`. `max_read` is
carried as a **maximum** in the totals, in every phase and route bucket, and
across the `--all` merge: summing it would answer *"how big was the biggest
read?"* with a number no single read ever had.

The first live reading, from the session that shipped this: **`max_read=11,036`
over 117 calls**, with `Bash` holding 198,191 of 206,266 bytes across 93 calls.
Reads here are many and small, not few and fat. One session is not a corpus — but
it is the first evidence of the kind P40b was rejected for lacking, and it points
away from a size threshold.

Nothing to do on upgrade. A transition line that omits the new fields stays
conforming; `run-cost.sh` reports them UNMEASURED rather than as a zero maximum.
