## What changed

- **`skills/verify/evals/`** — 3 evals: a planted bug that fails the test
  suite, a "sneaky" bug that keeps tests green but breaks the real CLI run
  (the rationalization trap — FAIL must not become PASS), and a clean control
  that must end `VERDICT: PASS` (guards against an always-FAIL verifier).
  Fixtures are stdlib-only mini-repos carrying their own spec + success
  metric.
- **`skills/work/evals/`** — 2 evals (feature kata, bugfix kata). Each
  fixture's `run-tests.sh` appends `RESULT=<PASS|FAIL> IMPL_SHA=<hash>` to
  `.check-log`, so "the test ran red BEFORE the implementation changed" is
  graded mechanically against the committed `baseline-sha` — no trust in the
  transcript.
- **Benchmark evidence** committed under `skills/<name>/evals/benchmarks/2026-07-29/`:
  1 real iteration, with-skill vs baseline. with_skill passed 10/10 (verify)
  and 8/8 (work) assertions; the baseline's misses were the machine-parseable
  verdict-line contract. with-skill runs re-executed against the v0.30.0
  skill text after rebase.
- **README — "Skill evals (manual release gate — not in CI)"**: the runbook
  (instantiate fixture copies, with-skill + baseline subagents, mechanical
  grading, commit the benchmark) and the cost rationale (~300–800k tokens per
  iteration).
- **Ledger**: two `type=fixture` learnings capture the fixture recipes
  (planted-bug mini-repo; auditable red→green kata).
- **Spec**: `.claude/flywheel/specs/p22-evals-pillar1.md` with a
  machine-checkable success metric.
