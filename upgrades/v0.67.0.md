## What changed

v0.65.0 shipped a gate that compares a plan's routes with what its run recorded,
and a question it refused to answer itself: **26 telemetry lines carry
`opus/xhigh`**, an effort `plan-route.sh` did not define. A route nothing can
rank is compared against nothing, so those transitions sat outside every
comparison the gate makes.

The owner has answered, and the CLI reference agrees: the effort levels are
`low`, `medium`, `high`, **`xhigh`**, `max`, with `ultracode` requesting `xhigh`
plus orchestration rather than being a sixth level. This repo's own
`docs/research/claude-code-loops.md` already said so in passing — the ladder
should have picked it up there.

`xhigh` is **inserted between `high` and `max`**, not appended: appending it
would rank `max` below it and silently invert every comparison at the top of the
ladder. The test asserts the position, not the membership, for exactly that
reason.

**`route-tiers.txt` is deliberately untouched.** The ladder and the tier table
answer different questions — the ladder is the vocabulary and ordering of legal
efforts, the tier table is policy about which `(model, effort)` pairs are named
tiers and which one the riskiest step of every plan is required to reach. Making
`opus/xhigh` a named tier would move that requirement for every future plan,
which is a policy change nobody asked for.

What this changes in practice: a plan may now route a task to `opus/xhigh`, and
`check-route-honored.sh` can rank a run recorded at it. On this repo's corpus
p13's three transitions stop reporting as *unrankable* and start reporting as
what they are — a run above the `opus/high` their plan bought, with no
`route_escalated_from`. They predate the cutoff, so they remain counted notices
and the tree stays green.
