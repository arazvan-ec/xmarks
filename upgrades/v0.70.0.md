## What changed

`plan-route.sh` has always rejected a plan whose task has no `- check:` — "a
route without a pass/fail check is not a task". That field was checked for
**presence** and never **run**. So the verdict "T4 is done" was produced by a
model reading its own work, over a field that, in 98 of this repo's checks,
usually already began with a runnable command.

`scripts/check-task-closure.sh` turns it into an exit code.

### Three verdicts that never collapse into one another

- **PASS** — a command was extracted from the check, matched the allowlist, ran, exited 0.
- **FAIL** — the same, and it exited non-zero.
- **UNRUNNABLE** — no allowlisted command in the check: prose only, or a command
  outside the boundary. Named and counted, never executed and **never read as
  green**. Reporting absence as honored is the mistake `check-route-honored.sh`
  exists to name.

One row per task, and the summary reconciles the count — N tasks in, N rows out.
A dropped item is visible exactly where the count stops matching.

### The allowlist is a security boundary, not a convenience list

A plan is repo content any PR can write, and `/flywheel:verify` runs on a
contributor's machine. Running `bash -c` over every backticked span would hand
it precisely the exposure `gate.sh`'s trust store exists to close. So only spans
matching `scripts/task-closure-allow.txt` are executed — this repo's own
`test-*`/`check-*` scripts, the plugin validator, and the two fixture
primitives. Everything else is UNRUNNABLE. Widen the file, with the reason, or
not at all: the gate has no inline exceptions.

An allowlisted **prefix** is not an allowlisted **command**, and the first cut of
this gate missed the difference: a pattern ending in an optional argument tail
matched `bash scripts/test-ok.sh && touch PWNED`, and the span then went to a
shell, which ran both halves. Caught in review on the PR that shipped it. Two
layers now, neither load-bearing alone — a span carrying a shell operator
(`& ; | ` `` ` `` ` $ ( ) < > \` or a newline) is refused *before* the allowlist is
consulted, and what survives is executed as argv with **no shell at all**.

### The cutoff, and what the gate does not grade

Plans added before `FLYWHEEL_TASK_CLOSURE_FROM` are corpus: reported, never
failed, and nothing may be rewritten to buy a green (P18, P48). The default sits
just before this cycle, so the first plan the gate grades is the one that
shipped it — and on that first contact it found two defects its own arms had
missed: the allowlist regex demanded a literal dot, so no `bash scripts/x.sh`
matched anything, and an unlintable pre-cutoff plan exited 2, which would have
left the gate permanently red on the corpus it ships into. Both have an arm now.

It grades the command's exit code, **not the prose around it**. A check reading
"`bash t.sh` fails on the new arms" is graded on `t.sh`, not on the word
"fails": a red-first expectation is transitional. A `check:` written from here on
states the condition that holds **at close**.

Also in this release: `plan-route.sh --json` carries each task's `check`
verbatim (the gate needs it, and a second reader of the plan format is how two
readers drift); `/flywheel:verify` gained a closure step; and the gate is wired
into CI, where `check-ci-gate-parity.sh` now counts 13 gates.

## Strategy

**Marketplace install:** nothing to do. The script and its allowlist arrive with
the plugin, and `/flywheel:verify` picks up the new step.

**Vendored install:** re-run `bash /path/to/xmarks/scripts/install-vendored.sh
<your-repo>`. The gate and `task-closure-allow.txt` are vendored together — with
the allowlist missing, every check reads as UNRUNNABLE and the closure verdict
silently means nothing.

**Either way, one habit changes.** A `check:` that is prose now reports
UNRUNNABLE rather than passing quietly. Write checks as a command the repo can
run — `bash scripts/test-thing.sh` — and keep the prose as the explanation
beside it, not instead of it. Nothing forces you to rewrite old plans: they are
corpus, and the cutoff leaves them alone.
