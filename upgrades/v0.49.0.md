## What changed

- **`skills/run/SKILL.md` step 1 — the write-path probe.** Before Rule 1, the
  declared store is proved reachable **read-only**: the connection opens and the
  target exists; a file store, the path is writable and inside the repo. Never a
  test row or a temp table. On failure the run appends a **blocker** transition
  to its ledger and stops — no Rule runs, nothing persists, and it **never falls
  back to another store**.

- **A missing data strategy stops the run there too**, pointing at
  `/flywheel:process`, instead of improvising a store around step 3.

- **`skills/process/` — the Access is probed before it is declared**, with the
  very tool about to be named; a probe that fails means DATA.md is not written.
  And **no database signal is now a detection, not a dead end**: the git-native
  store is proposed and confirmed rather than asked open-ended.

- **`scripts/session-start.sh` — the banner lists the repo's contracts**, name
  plus the first sentence of `## Purpose`, read at print time. The persistence
  line is never printed: that is where a connection string lives.

- **`skills/run/evals/` — eval 4**, on a fixture declaring a Postgres at port 1
  (reserved, never listening, so the refusal is deterministic and offline).

## Why the probe moved rather than being added

`run` step 3 already demanded proof that a write landed: *"a persist you did not
observe landing does not count as done."* This release applies that same
standard one step earlier and read-only. Nothing new was invented — the rule the
skill already stated is now enforced at the moment when failing is cheap.

Two rules are load-bearing in ways worth naming. **Read-only**, because a probe
that writes is a mutation the Guardrails did not approve, performed by the safety
check itself. **No silent fallback**, because a run that quietly switches store
scatters a process's records across two places with nobody told — half the rows
here, half there.

## The blocker line came from the test

Eval 4's grader was written as pure negatives: nothing persisted, nothing
staged, no Rule completed. P26's red-on-untouched invariant tumbled it — every
one of those is satisfied by a workdir nobody ever ran. Separating *"refused
correctly"* from *"never started"* required the run to leave a trace **before**
stopping, so that became a rule of the skill rather than an assertion in a test.

## Eval gate

All three suites that can see the change, green before the bump:

- `run` eval 1 — **4/4** (the happy path did not regress; the probe let a file
  store through)
- `run` eval 4 — **7/7** (new; seen **red at 4 FAIL** against the pre-probe
  skill, which persisted a row, staged the datastore, recorded a Rule completed
  and left no blocker)
- `process` eval 1 — **15/15** (its executor probed a file store's Access
  read-only before touching DATA.md)

Benchmarks under `skills/{run,process}/evals/benchmarks/2026-09-14-v0.49.0/`,
including two recorded deviations: one executor published its HTML report to an
artifact URL despite being scoped to its workdir, and both fail-opened on the
absent host task system.

## What is deferred, and the calibration finding

**A bare `/flywheel:run` still dead-ends on an empty slug** — that listing is
slice 2. `run`'s body ceiling fit the probe or the listing, not both, and the
banner already lists every contract at session start, so this was the cheapest
deferral available.

More useful to the next person retuning things: **this slice hit a byte ceiling
three times** — `run`'s body twice, `process`'s `worst` once — on ordinary
feature work, with every byte of argument already moved out to uncited
`docs/research/` notes. The ~300 B headroom rule in
`scripts/invocation-budget.txt` was a round number picked in v0.47.0; **~500 B
is what one feature actually costs**, measured here. `process worst` was
recalibrated to 11,200 on that basis, and the finding is written into the budget
file itself. A ratchet that fires on ordinary work is not tight, it is
miscalibrated.
