# Delegated review — the child session's prompt

Use this when a review runs in **another session** (`create_session`) rather
than in this one. A child that goes idle having posted nothing looks the same
whether it found nothing, could not post, or is still running (PR #95, P57).
The start comment removes the ambiguity in minute one.

Fill the placeholders and send the block below as the child's `prompt`. Pass
`model`, and name the effort in the text.

```text
{{REVIEW_COMMAND}}            (e.g. /code-review {{PR}} --comment, or /flywheel:review)

Repo {{OWNER}}/{{REPO}}, PR #{{PR}}, branch {{BRANCH}}. Route {{MODEL}}/{{EFFORT}}.

Posting: this container has NO `gh` CLI. Use the GitHub MCP tools, loaded with
ToolSearch ("select:mcp__github__add_issue_comment,mcp__github__pull_request_read,
mcp__github__pull_request_review_write,mcp__github__add_comment_to_pending_review").

1. FIRST, before reading any code, post one PR comment with add_issue_comment:
   "🔎 Review started — <what you will review>. fw-review-start"
   If that call fails, stop and say in your final message that GitHub is not
   reachable from this session. Do not review blind.
2. Review.
3. Post the findings as ONE review: pull_request_review_write method "create",
   one add_comment_to_pending_review per finding (file, line, severity, fix),
   then method "submit_pending" with event "COMMENT".
4. No findings → one PR comment saying so, naming what was checked.
5. Do not push code. End every GitHub post with a blank line, `---`, and
   `_Generated by [Claude Code](https://claude.ai/code)_`.
```

The marker `fw-review-start` is what `scripts/delegation-guard.sh` looks for:
a delegated review prompt without it gets a REVIEW ask naming this file.

The parent watches the PR. No start comment within a few minutes of the child
starting means the child cannot post — go read its transcript, don't wait.
